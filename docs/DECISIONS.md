# Decisions

Gaps and contradictions in `docs/SPEC.md`, resolved with Dan on 2026-09-23. Tests cite these IDs.

| ID | Topic | Decision |
|---|---|---|
| D1 | R9 / HV4 | 1,000 GB disk on 64 GB RAM is 1:15.6, inside the hot band 1:15–1:45. R9 asserts HV5 fires and HV4 does **not**. HV4 band unchanged. |
| D2 | Case 9 CCR | Add `ccrMode: 'unidirectional' \| 'bidirectional'`. Unidirectional: 11 hot + 2 frozen per site, 896 GB, 14 ERU. Bidirectional: each site also holds the follower copy (21 hot per site). Results report per site plus a total across sites. |
| D3 | ERU / total RAM | Counts Elasticsearch (data, masters, coordinating, ML), Kibana, and APM. Fleet Server is not counted. From §11.1 cases 5 and 10. Constant `eru.counted_components`. |
| D4 | "Data nodes" | Master and Kibana thresholds count all data-tier nodes, including frozen and vector nodes. From §11.1 cases 4 and 7. |
| D5 | Coordinating nodes | Added only when the user requests them (explicit count). |
| D6 | ML nodes | ROUNDUP(jobs / ml.jobs_per_node) + 1. §11.1 case 8 is tested as an add-on to case 1. |
| D7 | Fleet Servers | Needed + 1 (`fleet.redundancy_nodes`). |
| D8 | Forward options | New `ForwardOptions`: node template per tier (RAM, disk ratio, vCPU), sites, ccrMode, airGapped, fullLogsdb, fips, coordinatingNodes, growthHorizonYears. |
| D9 | Search/content | `WorkloadProfile.totalGb` for fixed corpora (case 6). No retention multiplier. |
| D10 | Warm ratio | Forward default 1:160 (`mem_disk.warm`). |
| D11 | vCPU | Forward default vCPU = RAM / 8 (`vcpu_per_ram_gb`). |
| D12 | LogsDB license | LogsDB needs no floor unless `fullLogsdb` is set (then Enterprise). |
| D13 | Fast mode | Retention past hot goes to frozen for logs and SIEM, to warm for metrics and APM. |
| D14 | Cold ratio | 1:160, same as warm (`mem_disk.cold`), Low confidence. |
| D15 | Growth | GB/day × (1 + growthPctPerYear/100)^years, horizon default 1 year. Shown as a MathStep. |
| D16 | bfloat16 | Element type, 2 bytes per dim + HNSW graph (kNN docs). |
| D17 | bbq_disk | kNN docs formula: clusters = n/384; centroid bytes = clusters × (5d + 14); quantized bytes = n × (d/8 + 16) × 2. No HNSW graph. Low confidence, conservative (docs say only a fraction must be in memory). |
| D18 | R6 fields | `WorkloadProfile.rolloverDays` (default 1) and `primaryShards` (default 1). `max_shards` also reports max data streams. |
| D19 | Heap cap | `heap_cap_gb` = 30 (spec said 31), per JVM docs: compressed-oops threshold '26GB safe ... as large as 30GB'. Off-heap per 64 GB node = 64 − 30 − 1 = 33 GB. HV2 errors above 30 GB. §11 impact: case 7 unchanged (BBQ 41.2/33 → 2+1 = 3 nodes; float32 832/33 = 25.2 → 26+1 = 27 nodes). R5 re-baselined: 2 × 33 = 66 GB; BBQ 66e9/412 = **160.19M** (was 155.3M); float32 66e9/8,320 = **7.93M** (was 7.69M). |
| D20 | Frozen local disk | Superseded by D27 for the disk default (now RAM × `frozen_local_disk_ratio`). Still true: HV4 does not check frozen. |
| D21 | Fast / expert (§10) | Replaced by one input model with progressive disclosure: each workload shows the §10 essentials (ingest, retention, replicas, index mode) and hides the rest under "More options". Deployment settings live in one shared section. v1 saved scenarios migrate automatically (fast inputs convert per D13). |
| D22 | Downsampling | The downsample factor is the share of data kept, in (0, 1]; 1 = none. Elasticsearch only downsamples TSDS, so a factor other than 1 on a LogsDB or standard workload is rejected (`downsampleProblem`). The UI shows the field only in TSDS mode and clears factors when leaving TSDS. |
| D23 | Results column (§10) | The whole results column is pinned when it fits the window, with no scrollbar of its own. Amended 2026-09-26 (REVIEW.md §2): the column shows the headline answer, totals, the cluster map, the three tightest constraints and the top hardware findings inline. The full constraint list, node table, all checks and the assumptions open in flyouts. The "Estimate, not benchmark" note stays visible under the column; the assumptions are still exported verbatim. |
| D24 | Growth | Forward: growth has its own step (horizon of Today, 1, 2, 3 or 5 years, plus a rate per workload with the size today and at the horizon); it no longer hides in workload or deployment menus. Reverse: new question "Years until full" (`years_to_capacity`, not in spec §5.3). It finds the largest t where every fixed workload grown by (1 + g)^t still fits, by bisection on the max GB/day solver; 0 if already over, unbounded with no growth. |
| D25 | Tier ratio overrides | Each scenario can override a tier's mem:disk ratio (forward: `NodeTemplate.memDiskRatio`; reverse: `HardwareConfig.memDiskRatio`). Blank uses the constant. Overrides flow through node sizing, reverse capacity and HV5, are named in the math ("scenario override") and the assumptions, and save with the scenario. HV4's tier bands stay on the constants, so an unusual override still warns. |
| D26 | Object storage | Cold and frozen keep data as searchable snapshots in an object store. The engine adds it automatically: one copy of cold + frozen data per site (no replicas, no headroom; cold → frozen is the same snapshot, so no double count). A scenario can override the size (`ForwardOptions.objectStorageGb`) for costing. Not counted in RAM or ERU. `object` is no longer offered as a node disk type (spec §7 lists it); saved scenarios convert it to SSD. |
| D29 | License tiers | Self-managed now offers only Basic and Enterprise; Platinum was removed (Dan, 2026-09-26). ML, cross-cluster replication and FIPS 140-3 move from Platinum to Enterprise (`license.floor.*`, carried forward with a note). `LicenseTier` is `'basic' \| 'enterprise'`. §11 impact: F8 floor platinum → enterprise; spec §5.6 lines for ML, CCR and FIPS read Enterprise. The results column no longer shows a separate "License floor" stat: Basic reads "Basic, no subscription"; otherwise the ERU count carries "Enterprise". |
| D30 | Platform cost (TCO) | Spec §2 lists pricing quotes as a non-goal; Dan asked for indicative cost (2026-09-26). The results column shows the subscription (ERU × price per ERU per year; Basic has none) with the price editable in place. A "Total cost" page adds hardware (servers per GB RAM plus local disk per TB by type, spread over amortization years), object storage per TB-month, hosting per node-month and operations FTEs, per year and over a term (default 3 years). Forward year N uses the cluster sized for N years of growth; reverse prices the given hardware every year. Prices are browser-only defaults on Configurations, overridable per scenario, and never enter `packages/constants` (list prices have no public source). Cost lives in `apps/web/src/cost.ts`, not the engine. The Markdown export includes cost only when the scenario's "Include cost" switch is on. |
| D28 | Hardware throughput overrides | Two optional scenario-level overrides for hardware-speed constraints, both Low confidence and Rally-required. `eventsPerSecondPerVcpu` (on `ForwardOptions` / `ReverseRequest`) replaces the `ev_per_s_per_vcpu` constant (default 1,500) when the customer has Rally benchmark data. `diskWriteMBps` (on `NodeTemplate` / `NodeGroup`) adds a `disk_write` constraint: `capacity = usable_nodes × MB/s × 86,400 / 1,000`; ceiling in reverse is divided by `(replicas+1) × index_ratio`. Neither field is required; when absent the constraint is omitted entirely. Network bandwidth dropped as too topology-dependent to model reliably. |
| D27 | Frozen tier model | Replaced the RAM×1500 object-store ratio with a disk-cache model: `nodes = ROUNDUP(data × cache_fraction / (disk_per_node / storage_overhead))`. Two new constants: `frozen_local_disk_ratio = 750` (GB local SSD per GB RAM) and `frozen_cache_fraction = 0.10` (fraction of frozen data that must fit in local cache, user-configurable via `ForwardOptions.frozenCacheFraction` / `ReverseRequest.frozenCacheFraction`). The 1:1500 RAM ratio modeled the full queryable corpus in RAM; the disk-cache model reflects how searchable snapshots actually work (only the hot-path slice needs local cache). `mem_disk.frozen = 1500` is retained for reference but no longer drives sizing. §11 impact: F3 re-baselined (5 frozen → 2; 3,056 → 2,864 GB; 48 → 45 ERU); F10 re-baselined (3 frozen → 2; 1,088 → 1,024 GB; 17 → 16 ERU); reverse "solves frozen jointly" re-baselined (573.1 → 91.64 GB/day). D25 ratio overrides do not apply to frozen under this model. The cache fraction must be above 0 and at most 1; the engine rejects other values. The UI edits it as "% cached" in the frozen row of Node sizes (forward) and next to the tier ratios (reverse), and new reverse frozen groups default their disk to RAM × `frozen_local_disk_ratio`. |
| D31 | Rollover | Data streams roll over when a primary shard reaches `datastream.rollover_max_primary_shard_gb` (50) or the index reaches `datastream.rollover_max_age_days` (30), whichever comes first, sized on the write tier's indexed GB/day after growth. A days value on the workload overrides both. Replaces the fixed 1-day default (`datastream.default_rollover_days`, removed). In reverse, shard count now caps max GB/day (bisection), since more ingest means more rollovers. HV8's small-shard note is skipped for single-primary streams that roll over on age. |
| D32 | Multiple sites on physical servers | New mode for several self-managed clusters. Servers are entered per role; nodes per server default to RAM ÷ `node_ram_practical_max_gb` for data and master roles and 1 for frozen, ML, Kibana, Fleet and APM (overridable). Failover reserves a whole server per tier. Relationship sets what each site holds: independent (own data), DR (standbys hold the primary's data) or active-active (every site holds all data); CCR sets the license floor. Each site is sized with forward mode on node templates from its servers, then checked against its servers; roles with no servers listed are reported as not placed, not as a shortfall. Headroom = largest multiple of today's data volume that fits every site (bisection on the fit check). Totals sum per site; ERU is summed per cluster. Sites can be identical (one form) or entered separately. |
| D33 | Compare deployment models | New mode sizing one site's servers under self-managed, ECK and ECE, shown as a trade-off table (fits, headroom, servers, ERU) with the best on each measure starred; no single winner. Self-managed: data servers split into ≤64 GB nodes; ERU = node RAM (D3). ECK: each server keeps `eck.k8s_reserve_ram_gb` (6) and `eck.k8s_reserve_vcpu` (1) for Kubernetes (cautious defaults, Low, carried forward); the rest is split into ≤64 GB pods; ERU = pod memory limits in GiB (P6 test added). ECE: master-role servers are the `ece.control_plane_hosts` (3) control-plane hosts needing `ece.control_plane_ram_gb` (80 GB: coordinator 32 + director 32 + proxy 16, from the ECE hardware page; spec §5.5's 28 GB multi-role reserve is not used); allocators planned to `ece.allocator_planning_fraction` (0.85); ERU = RAM of the allocator and control-plane hosts used. All models: masters, Kibana, Fleet and APM run one per server (quorum and HA pairs); failover reserves a whole server per tier. Lifts the original "self-managed only" MVP scope for these adapters. |
| D34 | Deployment model selector per mode | Server-based modes (Multiple sites) size self-managed, ECK and ECE directly: the selector sets the engine's host model for every site. Node-based modes (Size a workload, Test hardware limits) size self-managed only; picking ECK or ECE there opens Compare models with the same workloads and settings, because those models need server specs. ECH and Serverless stay disabled until their estimators exist. |
